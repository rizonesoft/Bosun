1. **[P2] Activation can be acknowledged before the UI callback exists.** `src/Bosun.Panel/Startup/SingleInstance.cs:141` substitutes `Task.CompletedTask` when `Activated` is null. The constructor starts listening before `PanelStartup.Begin` installs that callback at `PanelStartup.cs:94`. Two concurrent launches can therefore return `Forwarded` and exit 0 without the first UI receiving the request. Reproduce deterministically by starting the first `SingleInstance`, sending an activation before assigning `Activated`, then assigning it: the second receives success, but the request is permanently lost. Concurrent launches and ordinary thread scheduling can produce this ordering. Install the callback before accepting connections, or wait for callback readiness before acknowledging.

2. **[P3] Exceptions during activation bypass crash handling and are swallowed.** `src/Bosun.Panel/Startup/PanelStartup.cs:94` uses `Dispatcher.InvokeAsync`; its callback exceptions are stored in the returned task. The listener awaits that task and discards its exception at `SingleInstance.cs:153-162`. Contrary to the comment, the dispatcher crash handler does not report it, and observing the fault also prevents the unobserved-task handler from reporting it. Reproduce with a recording `StartupHost` whose `BringForward` throws, send an activation and pump the dispatcher: no report, crash notice or shutdown follows. Route activation failures explicitly through the UI crash policy. This is P3 for this candidate because the real window is deferred and its current callback returns immediately. [WPF exception behavior](https://learn.microsoft.com/en-us/dotnet/api/system.windows.threading.dispatcher.invokeasync?view=windowsdesktop-10.0).
