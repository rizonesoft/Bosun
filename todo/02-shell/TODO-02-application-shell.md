**Corrected 2026-11-15:** checked against the tree before the build. What the section said before is in its three items (a named mutex and activation pipe, the three handlers, the manifest); they are split and made exact below. The facts and the decisions, each with what reversing it costs:

- There is no window yet (`MainWindow` is `D02 T02 §4`'s), so "the first window comes to the front" can't be shown here: the first instance raises `SingleInstance.Activated` when a second launch asks, `App` answers it by showing, restoring and activating `MainWindow` when there is one, and the window's side (a minimised or hidden window comes back) is an item added to `D02 T02 §4` on 2026-11-15, with the two real processes in `D02 T02 §10`.
- One panel per user and logon session: the mutex is `Local\Bosun.Panel.<name>` and the pipe `Bosun.Panel.<name>.<session id>`, opened for the current user only (`PipeOptions.CurrentUserOnly`), where `<name>` is the user's SID. The environment variable `BOSUN_PANEL_INSTANCE`, when set, replaces the SID, so a test (or a second panel run from a checkout) never meets the operator's own running panel. Reversal cost: none.
- The first instance is whoever created the mutex, never whoever owns it: a panel that crashed holds no handle, so it never blocks the next one, and nothing waits on an abandoned mutex.
- The second launch sends the one word `activate` and exits 0. Before it sends, it lets the first take the foreground (`AllowSetForegroundWindow` with the pipe server's process id), since Windows refuses a background process that. If the first does not answer in 5 seconds (it is hung, or was just exiting), the second tries once more to be the first, and otherwise exits 3 having started nothing: two panels polling at once is the failure this section exists to prevent. Reversal cost: none.
- The pipe's reader is hostile-input code: it reads at most 64 bytes, for at most 2 seconds, acts only on `activate`, and a client that sends nothing, too much or anything else is dropped without the listener stopping.
- A crash report is text in the crash folder (`%LOCALAPPDATA%\Bosun\crash\`, or the folder the environment variable `BOSUN_PANEL_DATA` names, with `crash` under it, for tests): the time, the panel's version, the Windows and .NET versions, which handler caught it, and the exception with its inner exceptions and stacks. It never holds the environment, the command line or a user's name: the user's profile path, user name and the machine's name are replaced wherever they appear (a path in an exception message carries them). It is written temporary-file-then-replace, capped at 256 KB, and the folder keeps the newest 20 reports, so a crash loop can't fill the disk.
- After an exception on the UI thread the panel's state is unknown, and it can change the machine: it writes the report, says so in a message that names the report and offers to start the panel again, and exits with code 1. It does not carry on. An unobserved task exception is reported and observed, and the panel carries on (nothing on screen depends on a task nobody awaited). An exception on any other thread ends the process, as .NET does; the report is written first. Reversal cost: one handler.
- Steward's manifest asks for `requireAdministrator` (`app.manifest:12`), which the panel must not copy (`docs/specs/2026-11-07-control-panel-design.md:48`); its DPI lines are `:27-28`. The panel's also names Windows 10 and 11 as supported and the version 6 common controls, so the crash message is drawn as Windows 11 draws a message box.
- The checkpoint named `dotnet test Bosun.slnx --filter FullyQualifiedName~Startup`, which the test platform here does not take: it is `--solution Bosun.slnx --filter-class`.

- Steward's `AsyncCommand.Execute` is `async void` with nothing catching what the action throws, so a failed action is an unhandled exception on the UI thread, which in Bosun ends the panel (`D02 T02 §1`). - The scheduler is `src/Bosun.Core/RefreshScheduler.cs`, with nothing of WPF in it. It keeps no thread and no timer of its own: something outside ticks it (`IRefreshDriver`), and it runs whatever is due by a clock it is given. - A refresh is registered once with its name, its interval (`RefreshScheduler.Fast`, 5 s, for memory and the queue; `RefreshScheduler.Slow`, 30 s, for the others) and its work, and is then started and stopped. - When the panel exits, the scheduler is stopped: every refresh is stopped, work under way is cancelled, and nothing can start after. The tray's Exit does it before it asks the application to exit, and the application does it again on its way out however it ends.
- No page polls yet: the first are the Memory and Queue pages (`D03 T01 §2`, `D03 T02 §3`), which register with the scheduler through `PageBase`. Here the page side is proved with the tests' own page.

## 11. One desktop owner across smoke runs and captures

> **Started:** 2026-11-18T00:53:25Z

Filed 2026-11-18 at the operator's request ("be careful with the smoke tests that the tests do not clash, for example running 2 interface tests at the same time"). Inside one smoke run the tests already take turns (`tests/Bosun.Panel.E2E/TestAssembly.cs`, parallelization off), but nothing stops a second process: two smoke runs from two sessions, an Antigravity run beside a Claude one, or `scripts/capture-window.ps1` started while a smoke presses keys. Each takes the foreground, the pointer and the keyboard, so the two take each other's windows and a test fails on the other's input, or worse, keys land in the wrong window. The desktop gets one owner at a time: a named mutex per logon session, held for a whole smoke run and for each capture, with a record naming its holder, since a mutex can't name its owner (the queue's pattern, `D01 T01 §1`).

**Phase:** 3
**Needs:** none
**Surface:** no

Decisions, each with what reversing it costs:

- The lock's name is `bosun-desktop`, the mutex `Local\bosun-desktop`: the input desktop belongs to one logon session, so two sessions (a console and a remote one) never share a desktop and need not wait on each other. `BOSUN_DESKTOP_LOCK`, when set, replaces the name, as `BOSUN_PANEL_INSTANCE` does for the panel (`D02 T02 §1`), so a test of the lock never meets the operator's smoke or its own run's hold. A name is 1 to 64 of `a-z`, `0-9` and `-`, and anything else is refused: mutex names are case-sensitive and file names are not, so a name limited to lower case can't put two locks in one record file (the case `D01 T01 §1` met). Reversal cost: one name.
- The record is `%LOCALAPPDATA%\Bosun\run\<session>\desktop\<name>.json` (`schema_version` 1, `pid`, `process_start`, `command`, `repo`, `acquired_at`), the session from `ProcessIdToSessionId` as the queue's records are, and `process_start` the process's creation time as a FILETIME integer, the queue's form (`src/core.hpp`, `Record::process_start`), which C# (`Process.StartTime.ToFileTimeUtc()`) and PowerShell write alike. The default record is `run\<session>\desktop\bosun-desktop.json`. Reversal cost: one path.
- The record is advisory: the mutex is the only authority. A record that can't be written or removed is said once on stderr and changes nothing about holding or releasing, and the mutex is released in a `finally` on every way out. A reader names a holder only from a record whose `pid` is alive with that `process_start`; a missing, malformed or stale record gives "an unnamed holder". Reversal cost: none.
- A second owner waits, bounded, and says once, as soon as it finds the lock taken, who it waits for; at the bound it refuses naming the holder's pid, command and start time. `BOSUN_DESKTOP_WAIT_S` is a whole number of seconds from 0 to 86400, 0 meaning refuse at once when the lock is taken; empty or unset is 900 (a full smoke run with room); anything else (negative, a fraction, text, past 86400) is refused naming the variable, in both consumers, so every wait stays bounded. Waiting is the right default, since two runs that take turns both pass; a refusal after the bound beats a run that hangs. Reversal cost: a default.
- A process the holder starts inherits the hold through `BOSUN_DESKTOP_HELD=<name>:<pid>:<process_start>` and takes no lock of its own, because the smoke itself runs `capture-window.ps1` (`CaptureTests`), which would otherwise wait on its own parent until the bound. The inherited hold counts only when all four hold: its name is the lock name this process would take, the pid is alive with that start time, it is an ancestor of this process, and the lock's record names that same pid and start time. Anything else takes the lock as usual. Reversal cost: none.
- A Windows mutex belongs to the thread that took it, so the smoke's hold lives on a thread of its own (`DesktopHold`) that takes the mutex, waits for its release signal and releases it, whatever thread xunit constructs and disposes the fixture on. Reversal cost: none.
- A holder that dies leaves an abandoned mutex, which a waiter takes at once (`AbandonedMutexException` is ownership) and then writes its own record over the stale one. Reversal cost: none.

Decisions, each with what reversing it costs:

- A test that sends real input carries the xunit trait `Input=Real` (`[Trait("Input", "Real")]`, on its class or method); the default smoke run filters it out (`--filter-not-trait "Input=Real"`), and the input set is that trait alone. Reversal cost: one trait.

It is not a run of the plan: it starts no session and resumes nothing (the owner's rule of 2026-11-12). Reversal cost: `-Uninstall`.

- Each run, run or skipped, writes one record to `%LOCALAPPDATA%\Bosun\smoke\input-last.json` (`at`, `outcome`: `passed`, `failed`, `skipped-locked`, `skipped-in-use` or `stopped-in-use`, the counts, and the log's path), through a temporary file and replace; the log goes to `%LOCALAPPDATA%\Bosun\smoke\input-<date>.log`, the last 14 kept.
